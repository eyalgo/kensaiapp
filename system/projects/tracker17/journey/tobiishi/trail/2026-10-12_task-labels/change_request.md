# Change request — 2026-10-12_task-labels

*Opened from station `2026-10-12_task-labels` (item 4 of `tracker17 · nemawashi · 2026-10-07_tasks-in-a-project`). First change unit of that station; its reached-when 1 to 8 are one capability, so it is expected to be the only one.*

---

**Request:** Let the operator put labels on a task and take them off. The task page gains a label area: each label the task carries shows with a Remove button, and a text field with Add puts on one more, one at a time (SRS FR-23; UXD UX-F9). A task with no labels says so in a sentence, with Add in view (UXD UX-S6). A label is free text, must not be empty, is stored exactly as typed and compared exactly, and takes at most 200 characters (SRS FR-23, FR-40). Adding a label redirects to the task's page, which shows it, and puts the page's focus on the added label (SDD § 11 R-2). Adding a label the task already carries leaves the task as saved. Removing a label leaves the others. The task list row shows the labels the task holds. An empty label and a label over 200 characters are each refused on the task page where it was entered, with the typed text kept and the saved data unchanged. The label rules live in a new `domain/labels.py`, and the add and remove in the domain and application parts, not the web part (SDD § 4 TS-3). The saved data already holds each task's labels; this change adds the check that the data keeps the rule: saved data in which a task carries an empty label, a label over 200 characters or a repeated label is reported as unreadable at start, and none of it is loaded (SDD § 4 SD-5; SRS DR-6). Every string comes from the product's content record, none invented in code.

Tests ship with it: unit tests for the label rules; integration tests through the real server for the label area as shown (labels with Remove and Add, and the no-labels sentence with Add in view), an add, a repeated add, a remove that leaves the others, the list row showing the labels, and the two refusals with the typed text kept; a start-check test that writes saved data with an empty label, one over 200 characters and a repeated label, one case at a time, and finds the start reporting each as unreadable and loading none of it. An end-to-end test adds a label and finds the page's focus on the added label (SDD § 11 R-2, `SDD.md:L755`). An end-to-end test enters a label holding `<`, `&` and `"` and finds the task's page and the project's list showing it as typed (NFDR QC-36). `python3 products/tracker17/tests/timed_run.py` times a label add among its actions at 1,000 tasks and exits 0 (NFDR QC-48). `pytest products/tracker17/tests/` and `pytest products/tracker17/tests/e2e/` each exit 0, run on a `git archive HEAD` copy that is `git init`-ed, since the repository-ignore test needs a git repo.

**Must not be weakened or added:** no status move, delete, filter or sort control, summary or comment is added; the filter that narrows by label stays with its own station. The saved form of a task and of the People list must not change (the `labels` list already saved stays as it is), and no existing test is weakened to fit. The edit form of title, priority, assignee and due date stays as `edit-task-fields` left it.

**Left to later stations:** the filter that narrows by label (`tracker17 · nemawashi · 2026-10-11_narrow-and-sort`); status moves (`tracker17 · nemawashi · 2026-10-07_status-moves`); comments and their saved-comment start check (`tracker17 · nemawashi · 2026-10-07_comment-on-a-task`).

**Sizing:** the acceptance boundary is one operator capability, labelling a task from its page (SRS FR-23, FR-40; SDD § 4 SD-5, TS-3; UXD UX-F9, UX-S6; station reached-when 1 to 8). The label rules, the add and remove with their refusals, the list row, the start check on saved labels and the escape, focus and timing proofs are one operation's input, error paths and read-back, and the label rule they share keeps them in one merge (`pm_right_size.md` § *Right-size to one honest merge*). It builds on the task page, `domain/tasks.py` and the edit form already landed and fits one development flow. The filter, status and comments are different operations with their own acceptance, held elsewhere.
