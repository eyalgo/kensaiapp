# Change Spec — Moving a task along its allowed status moves

**Date:** 2026-10-19
**Category:** feature
**Behaviour:** changing
**Request:** Let the operator move a task through its status workflow from any list row or from the task's own page. Add `products/tracker17/domain/workflow.py` as the one home of the status workflow (SRS FR-18, FR-19): the allowed moves from each status (`todo`→`in-progress`, `todo`→`cancelled`, `in-progress`→`done`, `in-progress`→`cancelled`, `in-progress`→`todo`; `done` and `cancelled` offer none) and, for any other move, a refusal with its reason, a move to the status the task already has included. Every list row and the task's page then offer the allowed moves other than `cancelled` as buttons named by the status they lead to. A press saves the move and leaves the operator at the moved task's row (or at the task's moves on its page), with the new status shown and one line naming what changed (SDD § 4 EX-5, EX-7). A task moved to `done` is no longer marked overdue (AC-13's third case), also for the overdue filter and the summary count where those exist at this point.

Tests: a unit test per allowed move and per refused move (every other from/to pair among the four statuses, the same-status move for each status included), each asserting the refusal reason or the saved result; an integration test that a row and the task's page offer the right buttons per status (`todo`: `in-progress`; `in-progress`: `done` and `todo`; `done` and `cancelled`: none; no `cancelled` button anywhere) and that a press saves the move, shows the new status and one line naming what changed; a test, with today's date set by the test, that a task due yesterday and moved to `done` is not marked overdue on its row. `pytest products/tracker17/tests/` must exit 0 from the repository root.

What must not be weakened: the workflow rule is written once, in `domain/workflow.py`, and no page, route or test restates the table. No `cancelled` button appears on any page and no confirmation is built here, because a move to `cancelled` must never save unconfirmed (EX-6) and no page shows a control before its slice (EX-12); the workflow rule itself keeps every move. No out-of-date-move handling and no change to `tests/timed_run.py`. The saved data format must not change except for the status. Files other than `domain/workflow.py`, the pages and routes that offer the moves, and their tests stay as they are.
**Language resolution:** Python — step 1, `project.md` `Languages:` — `core/doctrine/engineering/languages/python/README.md` opened, and its six concern files scanned for a line that fixes how a fact is rendered; no rule below renders a language-level fact

## Change Summary

The operator can move a task from `todo` or `in-progress` along the moves the workflow allows. Every row of a project's task list, and the task's own page, offer those moves as buttons, except `cancelled`. A press saves the move, keeps the operator where they were, and confirms the move in one line. The workflow rule lives once, in the Status workflow feature's entry module. It still allows the move to `cancelled`, but no page offers one yet.

Paths below are relative to the product root, the directory `system/projects/tracker17/project.md` `Product path:` names. "The records" are that product's `docs/fdr.md`, `docs/SRS.md`, `docs/SDD.md`, `docs/nfdr.md`, `docs/UXD.md` and `docs/CONTENT.md`.

## Rules

### The workflow rule

- **CP-293:** The status workflow is stated once, in the Status workflow feature's entry module `domain/workflow.py` (SDD § 4 TS-3, feature word `workflow`). For a task's current status it gives the allowed moves, in this order: `todo` → `in-progress`, `cancelled`; `in-progress` → `done`, `cancelled`, `todo`; `done` → none; `cancelled` → none (SRS FR-18; fdr R-53, R-54). The rule keeps the move to `cancelled`, though no page offers it in this change (CP-301).
- **CP-294:** Every other from/to pair among the four statuses is refused, and the state is unchanged. That is 11 pairs: the four same-status moves (`todo`→`todo`, `in-progress`→`in-progress`, `done`→`done`, `cancelled`→`cancelled`), `todo`→`done`, and every move out of `done` or `cancelled` to another status (`done`→`todo`, `done`→`in-progress`, `done`→`cancelled`, `cancelled`→`todo`, `cancelled`→`in-progress`, `cancelled`→`done`) (SRS FR-18; fdr R-55). The refusal is a typed refusal raised by `domain`. `application` hands it to `web`, and `web` maps it to its reason by type (NFDR QC-5; SDD § 4 OB-4).
- **CP-295:** An accepted move changes the moved task's status and nothing else. Its title, priority, assignee, labels, due date, creation time and comments are unchanged, and so is every other task, project, the assignee list and the operator's name. In the saved data, the moved task's saved status word is the only value that differs. After a stop and a start on the same saved data, the task has its new status (fdr R-15, R-52).
- **CP-296:** Unit tests check the rule with no file and no clock (SDD § 4 TS-1): one test for each of CP-293's five allowed moves, asserting the resulting status, and one for each of CP-294's 11 refused pairs, asserting the refusal and an unchanged state. A test names each pair with its expected outcome as a case. That is not a second statement of the rule (see Locked Answers, Gap 2).

### The moves a page offers

- **CP-297:** Every row of a project's task list, and the task's page, show the task's current status with one button for each move CP-293 gives for that status, except `cancelled`. The buttons follow CP-293's order, and each button's visible label is the target status word, lowercase, as written: `todo` offers `in-progress`, `in-progress` offers `done` then `todo`, and `done` and `cancelled` offer none (UXD UX-I1, UX-F4; CONTENT.md RN-8). No page decides which moves a status allows: the buttons come from what the workflow rule gives (SDD § 4 EX-7; § 3, `web` row, "it never works out which moves are allowed").
- **CP-298:** Each move button's accessible name is `Move '<title>' to <status>`, where `<title>` is the task's title as saved and `<status>` is the button's visible label. For example, the `in-progress` button of a task titled `Set up CI` is named "Move 'Set up CI' to in-progress" (CONTENT.md § Accessibility of text, the first rule).
- **CP-299:** The task's page shows the task's current status in words, beside its moves. A task in `done` or `cancelled` shows its status and no move button (UXD UX-S6; SDD § 4 EX-9, "Status … written in text").
- **CP-300:** Each move button can be reached with Tab and pressed with Enter or Space, and the tracker adds no keyboard shortcut (UXD UX-I6; SDD § 4 EX-8; SRS NFR-12). Each move button's pointer target is at least 24 by 24 CSS pixels (UXD UX-A6).
- **CP-301:** No page shows a button labelled `cancelled`, a control that moves a task to `cancelled`, or a confirmation for any move (SDD § 4 EX-6, EX-12).

### Pressing a move

- **CP-302:** Pressing a move button saves the move, and only then shows it as done (fdr R-18; SDD § 4 SD-2). The submission is answered by sending the browser to a page address (SDD § 4 RT-8). That page is the one the button was on: the project's page for a row, and the task's page for the task's page.
- **CP-303:** After a move pressed on a row, the project's page opens at the moved task's row. The row shows the new status and the moves the new status offers under CP-297. Keyboard focus is on an element within that row, set with the `autofocus` attribute, and the page's address carries no fragment (SDD § 4 RT-9). The completion line is the accessible description of the element that has focus, and the line itself does not take focus (SDD § 4 EX-5, EX-14).
- **CP-304:** After a move pressed on the task's page, that page opens at the task's status and moves. The status shown is the new one, and the moves are the ones the new status offers. Focus and the completion line follow CP-303's rule for that place (SDD § 4 EX-5, EX-14, RT-9).
- **CP-305:** The completion line reads `You moved '<title>' to <status>.`, where `<title>` is the task's title as saved and `<status>` is the status it moved to. For example: "You moved 'Set up CI' to done." (CONTENT.md § Message patterns, Completed, the second example; UXD UX-I4). The page shows exactly one completion line. A title holding `<` or `&` shows as typed (fdr R-112).
- **CP-306:** Reloading the page a move landed on, or going back or forward to it, shows the same completion line again and moves nothing (fdr R-106; PD-11).
- **CP-307:** Overdue follows the saved status (fdr R-68). After a task due before today is moved to `done`, its row shows no "Overdue" word, though it did before the move. After an overdue task moves from `in-progress` to `todo`, its row still shows "Overdue". The test sets today's date by handing the tracker a clock, and patches no name inside a part (SRS AC-13, third case; SDD § 4 TS-2; NFDR QC-28).

### A move that is refused, or that fails

- **CP-308:** A move is checked against the task's status as saved when the move is applied, never against what the page showed (fdr R-102). A pressed move that CP-294 refuses for the saved status changes nothing in the saved data. That includes a move pressed on a page loaded before another tab moved the task. The page that answers is the page the button was on. It opens at the task's row, or at the task's status and moves, with focus there, and it shows the refusal's reason in plain words as that element's accessible description (SDD § 4 EX-4, EX-14; fdr R-100). The reason's words are the content stage's, under CONTENT.md § Message patterns, Error (a refusal). This spec does not require the reason to say the page is out of date or to offer a reload (see Out of Scope).
- **CP-309:** The status a move submission names can be any value at all, and every case is decided. If it names one of the four statuses, CP-293 or CP-294 decides. If it names something else, or nothing, the move is refused, changes nothing, and is answered as CP-308 answers.
- **CP-310:** A move submitted for a task identity that no task holds changes nothing and is answered with the not-found page (fdr R-103, R-105; UXD UX-S10).
- **CP-311:** When a move fails for a reason other than a refusal, for example because the save fails, the saved data and the tracker's state are as before the press. The console shows a message naming the move and the error, and the browser says in plain words that the move did not happen and nothing was changed. No Python error text reaches the page (fdr R-107, R-108; NFDR QC-56, QC-57; SRS AC-18). The words are the content stage's, under CONTENT.md § Message patterns, Error (a failure that is not a refusal).
- **CP-312:** A test at NFDR layer 3 sends a move that CP-294 refuses through the tracker's request path, in the stale-tab case: the page showed `todo` and offered `in-progress`, and another tab had already moved the task to `in-progress`. The test asserts that the saved data is byte-for-byte the same before and after, and that the page that answers shows the refusal's reason (NFDR QC-5, QC-38; SRS AC-12, "one per refusal").

## Out of Scope

- **The `cancelled` button and its in-place confirmation.** UXD UX-I1 says every row and the task's page offer "exactly the moves allowed", and SDD § 6 S-4 and UXD UX-I2 put the move to `cancelled` behind a confirming press. The request rules both out: "No `cancelled` button appears on any page and no confirmation is built here". Today the product offers no move at all (`web/pages.py:558-573`, `:1078-1088`). Handed on as a record gap in `deferred_decisions.md`.
- **The out-of-date wording and the reload offer.** UXD UX-F4's failure and recovery says a refused move "says the task's status has changed and offers a reload". UXD UX-I3 and CONTENT.md § Message patterns, Error (the fifth refusal example) say the same, and SDD § 6 S-4 says a move from an out-of-date page "is refused, says the status has changed, and offers a reload". The request rules it out: "No out-of-date-move handling". CP-308 still refuses such a move, with a reason, against the saved status, and CP-312 tests it. Today the product has no move (same lines). Handed on as a record gap.
- **The overdue filter, the summary's overdue count, the All tasks list, and a moved task leaving a status-filtered list.** fdr R-88, R-96 and R-99, SRS AC-13's agreement across all three views, UXD UX-S7 and UX-F4's last bullet all bind views the product does not have yet: `grep -rni 'filter\|summary' web/*.py application/*.py` finds none. The request asks for the overdue effect on them only "where those exist at this point", and none does. Handed on as a record gap.
- **End-to-end tests for moves.** No record requires one of this change: SDD § 6 S-4 asks for end-to-end tests only of the `cancelled` confirmation. This spec requires none, and design may add one.
- **No new saved-data rule.** Any of the four statuses stays readable at start, whatever moves led to it, so SDD § 4 SD-5's added test is not triggered. The saved data format does not change (CP-295).
- **Deleting a task or a project, and their confirmations** (`delete-and-rename`). **Undo of any move** (UXD UX-I2: none exists).

## Locked Answers (the divergence record — self-review 2026-10-19)

- **Gap 1 — the request's file fence (b):** The request says files other than `domain/workflow.py`, the pages, the routes and their tests "stay as they are". CP-316 also makes moving a task one `application` action, which `application`'s re-exports carry to `web`. *Because* `web` may not import `domain` (NFDR QC-16), and every action is one `application` call that applies a `domain` rule (SDD § 3, `application` row). A move built inside the request's fence would fail the layer-6 import walk. The fence's intent is kept as observable outcomes: saved data and its format (CP-295), every other feature's pages, and `persistence` and `main` stay as they are. The test files the records require are named in Gaps 5 to 8.
- **Gap 2 — "no page, route or test restates the table" (b):** Read as: no part other than the workflow rule decides which moves are allowed (CP-297, CP-316). Tests name each pair with its expected outcome as a case (CP-296). *Because* the request's own test list asks for one test per pair and a per-status button check, and those name the pairs. Forbidding tests to name pairs would contradict the tests it asks for, while what the fence protects, one definition that code consults, holds either way (SDD § 4 EX-7).
- **Gap 3 — button order (b):** `in-progress` offers `done` then `todo` (CP-297). *Because* that is the order SRS FR-18's table lists the moves in, and the request lists them the same way. The order is reversible and touches no saved data.
