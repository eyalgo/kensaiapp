**Request:** Let the operator set and change their own name on the People page. Saving a name stores it as the one operator name, and saving a different one replaces it; the name is stored exactly as typed. A blank name, whether empty or only whitespace, and a name over the length FR-40 sets for the operator's name are each refused on People with the reason, the typed text kept in the field and the saved name unchanged (SRS FR-27, FR-39, FR-40; UXD UX-F8, UX-I3). The operator name is part of the saved data (SRS DR-5, AC-17): it survives a stop and a start, and a start on data saved before this change loads with no name set and keeps its projects, tasks, labels and people. The name rule lives in the domain and the set action in the application part, not the web part (SDD § 4 TS-3), and saved data holding a blank or over-long operator name is reported as unreadable at start (SDD § 4 SD-5; SRS DR-6). Every string comes from the product's content record, none invented in code ("your name", CONTENT.md § 158). Nothing about comments is built here; the saved name is what the next station's comment form will write under.

An end-to-end test in `tests/e2e/test_people.py` sets the name in the browser, sees it again after reload, and sees a blank one refused with the typed text kept. The two absence checks in `tests/integration/test_people_pages.py` (L115 and L441) drop `"your name"` from their lists, the one existing-test change this makes true. `pytest products/tracker17/tests/` exits 0, run on a `git archive HEAD` copy that is `git init`-ed, since the repository-ignore test needs a git repo.
