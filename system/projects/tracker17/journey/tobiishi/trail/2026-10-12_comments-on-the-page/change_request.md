# Change request — 2026-10-12_comments-on-the-page

*Opened from station `2026-10-12_comments-on-the-page` (item 2 of `tracker17 · nemawashi · 2026-10-07_comment-on-a-task`). First change unit of that station; its reached-when 1 to 8 are one capability, so it is expected to be the only one.*

---

**Request:** Let the operator write comments on a task and read them on the task's page. The page lists the task's comments oldest first, each with its author and the time it was written in the machine's local time, and shows a form below the newest comment with a sentence beside the text field naming the most characters a comment holds, the same number as the field's `maxlength` (SDD § 6 S-3; UXD UX-F7, UX-F8). Adding a comment saves it under the saved operator name, and after Add the page opens with the new comment in view and keyboard focus on it. After the name is changed on People, earlier comments keep the name they were written under and a new one carries the new name. With no name set, a notice above the form says a name is needed and links to People; a comment with no name set, and a blank comment (empty or whitespace only), are each refused with the reason shown, nothing saved and the typed text kept in the field. No control edits or deletes a comment. The Comment entity is part of the saved data as SDD § 3 states it, and saved data holding a comment that breaks a comment rule is reported unreadable at start (SDD § 4 SD-5), not repaired or dropped. `domain/comments.py` is the Comments feature's entry point (SDD § 4 TS-3): the comment rules live in the domain and the add action in the application part, not the web part. Every string comes from the product's content record, none invented in code.

Tests ship with it: unit tests for the comment rules; integration tests through the real server that a task's page lists comments oldest first with author and local time and shows the form below the newest with the maximum-length sentence equal to the field's `maxlength`; that adding a comment saves it under the saved name and shows it, read back from the saved data; that after a rename earlier comments keep the earlier name and a new one the new name; that with no name set the notice and the People link show and a comment is refused, and that a blank comment (empty and whitespace only) is refused, each with nothing saved and the typed text kept; that no edit or delete control for a comment is in the built page, on a page that has comments; and a start-check test, in `tests/integration/test_saved_data.py` or beside it, that saved data holding a comment that breaks a comment rule is reported unreadable at start and that data saved before this change still loads with its projects, tasks, people and name. End-to-end tests in `tests/e2e/` add a comment to a task whose comments fill more than the window and find the new comment in view with keyboard focus on it, and fill a comment to its maximum with line breaks and find it saved whole (SRS AC-20). `pytest products/tracker17/tests/` exits 0, run in a fresh clone checked out at the commit under test (`core/roles/CROSS_ROLE.md` § *Every seat*).

**Must not be weakened or added:** the timed run is not extended: `tests/timed_run.py` and its test stay byte-identical. No existing People or task-page test is deleted, skipped or loosened, and the operator-name behaviour is unchanged. No threaded replies, no deleting a comment with its task, and no wording change outside the comment text the content record names. The saved-data shape changes only as SDD § 3's Comment entity states.

**Left to later stations:** the 1,000 × 20 timed run and the assignee timing (`tracker17 · nemawashi · 2026-10-07_comment-on-a-task`, item 3 `full-volume-run`); deleting a task with its comments (`tracker17 · nemawashi · 2026-10-11_delete-and-rename`); the unreadable-data pages (`tracker17 · nemawashi · 2026-10-11_protect-saved-data`).

The list, the form, the add, the two refusals, the earlier-name rule, the missing edit control, the saved shape and its start check share one comment rule and one saved entity, so they stay in one merge (`pm_right_size.md` § *Right-size to one honest merge*).
