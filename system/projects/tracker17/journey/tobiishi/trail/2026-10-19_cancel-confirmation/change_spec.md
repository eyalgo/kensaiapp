# Change Spec — The `cancelled` button and its in-place confirmation

**Date:** 2026-10-19
**Category:** feature
**Behaviour:** changing
**Request:** Add the `cancelled` button to every list row and to the task's page, wherever the workflow rule allows that move (a task in `todo` or `in-progress`; none for `done` or `cancelled`), and make its first press open the in-place confirmation (SDD § 4 EX-6, UXD UX-I2) instead of saving. The confirmation shows in view, in this order: its sentence, its confirming control, its back-out control, with focus where UX-I2 places it. The confirming control saves the move to `cancelled` and shows the new status with one line naming what changed. Backing out restores the button and returns focus to it. A first press for a move the task no longer allows opens no confirmation and saves nothing.

Remove the pages' own withholding of `cancelled` (`_WITHHELD_MOVES` in `products/tracker17/web/pages.py` and its filter in `_move_forms`), so the moves a page offers equal the workflow rule's allowed moves (`domain/workflow.py`) for each status and no page keeps a second rule about them (SDD § 3 `web`). Run the browser tests the previous change landed unrun (`tests/e2e/test_moves.py`) and add the end-to-end focus tests: focus on opening the confirmation, focus on backing out, and a double press on the first button of a row far down a list scrolled part-way never confirms.

Checkable when done: `grep -n "_WITHHELD_MOVES" products/tracker17/web/pages.py` prints nothing; integration tests cover the `cancelled` button per status, the first press, confirming, and the stale first press; `pytest products/tracker17/tests/e2e/` (the whole folder) exits 0 on a machine where layer 5 runs (NFDR § 9: macOS, or the Debian/Ubuntu releases SDD § 4 RT-4 lists, with the browser libraries installed; on a machine where it does not run, that folder is a missing prerequisite and this item is checked on one that does); `pytest products/tracker17/tests/` exits 0 from the repository root.

Must not be weakened: the workflow rule stays written once, in `domain/workflow.py`, and no page, route or test restates the table. The saved data format stays as it is except for the status. There is no out-of-date-move handling and no change to `tests/timed_run.py`. Deleting a task or a project gets no confirmation here; the confirmation built must be reusable by that work but is not extended to it. Files other than the pages and routes that offer or confirm moves, `domain/workflow.py` if a gap shows, and their tests stay as they are.
**Language resolution:** Python — step 1, `project.md` `Languages:` — `core/doctrine/engineering/languages/python/README.md` opened, and its six concern files read for a line that fixes how a fact is rendered; no rule below renders a language-level fact

## Change Summary

Every row of a project's task list, and the task's own page, now offer the `cancelled` move wherever the workflow rule allows it. The first press saves nothing. It opens the same page with a confirmation in the button's place: a sentence, then a control that confirms, then a control that backs out. Confirming saves the move. Backing out restores the button. The pages stop withholding `cancelled`, so the moves a page offers are exactly the ones the workflow rule gives. The browser tests for moves run for the first time, with new ones for the confirmation's focus and its double press.

Paths below are relative to the product root, the directory `system/projects/tracker17/project.md` `Product path:` names. "The records" are that product's `docs/fdr.md`, `docs/SRS.md`, `docs/SDD.md`, `docs/nfdr.md`, `docs/UXD.md`, `docs/DESIGN.md`, `docs/CONTENT.md` and `docs/adr/`.

## Rules

### The `cancelled` button

- **CP-319:** Every row of a project's task list, and the task's page, offer one button for each move the workflow rule gives for the task's saved status, `cancelled` included, in the rule's order. A `todo` task offers `in-progress` then `cancelled`. An `in-progress` task offers `done`, then `cancelled`, then `todo`. A `done` or `cancelled` task offers none (fdr R-53, R-54, R-56; UXD UX-I1; SDD § 4 EX-7). The `cancelled` button's visible label is `cancelled`. Its accessible name is `Move '<title>' to cancelled`, with `<title>` the task's title as saved (CONTENT.md § Accessibility of text, the first rule). No page keeps a rule of its own about which moves to offer. Today the pages withhold `cancelled` through `_WITHHELD_MOVES` (`web/pages.py:603`) and its filter (`web/pages.py:609`). After this change `grep -n "_WITHHELD_MOVES" products/tracker17/web/pages.py`, run from the repository root, prints nothing (SDD § 3, `web` row, "it never works out which moves are allowed").
- **CP-320:** The `cancelled` button, the confirming control and the back-out control can each be reached with Tab and pressed with Enter or Space. The tracker adds no keyboard shortcut (UXD UX-I6; SDD § 4 EX-8; SRS NFR-12). Each of the three has a pointer target of at least 24 by 24 CSS pixels (UXD UX-A6; SDD § 4 EX-9).

### The first press opens the confirmation

- **CP-321:** A press of the `cancelled` button saves nothing. The saved data is byte-for-byte the same before and after. The press is answered with the page the button was on: the project's page for a row, and the task's page for the task's page. That page shows the confirmation in the place where that task's `cancelled` button stood. The confirmation replaces only that one button. Everything else on the page is as it is without a confirmation: the task's other move buttons, every other row, and every form. The page shows no completion line (CONTENT.md § Completed, "An action that only reads … produces none"; SDD § 4 EX-6, RT-8; UXD UX-I2).
- **CP-322:** The confirmation has three parts, in this order: its sentence, its confirming control, and its back-out control (UXD UX-I2). The sentence reads `Move '<title>' to cancelled? A cancelled task can't be moved again.` The confirming control reads `Move to cancelled`. The back-out control reads `Back out` (CONTENT.md § Needs confirming, the fourth example; § Terminology, "Back out"). `<title>` is the task's title as saved when the page is built. A title holding `<`, `&`, `"` or `'` shows as typed, in the sentence and in every accessible name (fdr R-112; SDD § 4 SEC-4). No part of the confirmation reads "Cancel", "OK", "Yes", "No" or "Confirm" (CONTENT.md § Terminology; UXD UX-I2).
- **CP-323:** The sentence covers the whole spot the `cancelled` button stood in, and is at least as tall as that button. The confirming control is as tall as the `cancelled` button was (UXD UX-I2; DESIGN.md § Components, `confirm-strip`, RN-25). The confirmation takes DESIGN.md's `confirm-strip` look, with a `button-confirm` confirming control and a `button-secondary` back-out control (SDD § 4 EX-10).
- **CP-324:** When the confirmation opens, keyboard focus is on its sentence, and the sentence is in view. That holds on a list scrolled part-way, for a row far down it (SDD § 4 EX-6; UXD UX-I2). The sentence is not a stop in the Tab order (SDD § 4 RT-9). Focus is never on the confirming control when the confirmation opens. From the sentence, one Tab reaches the confirming control, and a second Tab reaches the back-out control (UXD UX-I2). While the sentence has focus it shows the same focus ring a control does (DESIGN.md § Components, the focus rule; RN-25). The page sets focus on exactly one element. Pressing Enter or Space again, with focus on the sentence, changes nothing: no save, and the confirmation stays (UXD UX-I2, "a repeated Enter or Space changes nothing").
- **CP-325:** A double click on the `cancelled` button never confirms. The first click opens the confirmation, and the second lands on the sentence. Nothing is saved, and the confirmation is showing afterwards. This holds on a short page and on a list scrolled part-way, for a row far down it (SDD § 4 EX-6; UXD UX-I2).
- **CP-326:** A page shows at most one confirmation. Reloading the page the confirmation is on, or going back or forward to it, saves nothing (fdr R-106; SDD § 4 RT-8). While the task's saved status still allows the move to `cancelled`, a reload shows the same confirmation with focus on its sentence.

### Confirming and backing out

- **CP-327:** Pressing the confirming control saves the move to `cancelled`, and only then shows it as done (fdr R-18; SDD § 4 SD-2). The move changes the task's status and nothing else: in the saved data the task's status word is the only value that differs (fdr R-15, R-52). The press is answered with the page the confirmation was on. A row's confirmation lands on the project's page at that task's row. The task's page lands at the task's status. In both, the status shown is `cancelled`, the task offers no move button, and no confirmation shows. Keyboard focus is on the task's status in words, which is in view and is not a Tab stop. The completion line reads `You moved '<title>' to cancelled.` (CONTENT.md § Completed). It is that focused element's accessible description, and it does not take focus (SDD § 4 EX-5, EX-14; UXD UX-I4). The page shows exactly one completion line. Reloading this page shows the same line and saves nothing (fdr R-106).
- **CP-328:** A task due before today and confirmed to `cancelled` is no longer marked overdue. Its row shows no "Overdue" word, though it did before the move. The test sets today's date by handing the tracker a clock, and patches no name inside a part (fdr R-68; SRS AC-13, third case; SDD § 6 S-4, *Reached when* and *Command*; SDD § 4 TS-2; NFDR QC-28).
- **CP-329:** Pressing the back-out control saves nothing, and the page shows no completion line (CONTENT.md § Completed). It is answered with the same page and no confirmation. The `cancelled` button is back in the spot it stood in, keyboard focus is on that button, and the button is in view (SDD § 4 EX-6; UXD UX-I2). Reloading that page saves nothing.
- **CP-330:** Only a press of the confirming control saves a move to `cancelled`. Any other request that asks to move a task to `cancelled` saves nothing. That includes a press of the `cancelled` button, and a submission to the move address shaped the way the other moves are sent. Such a request is answered as CP-321 or CP-331 answer a first press (SDD § 4 EX-6; UXD UX-I2). Today a move submission naming `cancelled` saves the move at once: `web/routes.py:631-665` hands any status to the tracker (Verified Claims). Every move to another status still takes effect on its first press (UXD UX-F4, "A move to `done` takes effect on the first press").

### A press that is out of date, refused, or fails

- **CP-331:** A first press is checked against the task's saved status when the request is applied, never against what the page showed (fdr R-102). Where that status no longer allows the move to `cancelled` (the task is `done` or `cancelled`), no confirmation shows and nothing is saved. The saved data is byte-for-byte unchanged. The answer is the page the button was on, opened at the task's row or at the task's status, with focus there. The move refusal's reason for that saved status is the focused element's accessible description (SDD § 4 EX-4, EX-6, EX-14; UXD UX-I3; fdr R-100). A page opened at a confirmation's address, while the task's saved status does not allow the move, answers the same way. Where the saved status still allows it, the confirmation opens. A page that showed the task in `todo`, pressed after another tab moved the task to `in-progress`, opens the confirmation.
- **CP-332:** A press of the confirming control is checked against the task's saved status when it is applied (fdr R-102). Where the saved status is `todo` or `in-progress`, the move is saved as CP-327 says. That includes a confirmation opened while the task was `todo`, after another tab moved it to `in-progress` (fdr worked example, "Tab 1 then asks to move T to `cancelled`"). Where the saved status is `done` or `cancelled`, the move is refused and nothing is saved. The answer is as CP-331's.
- **CP-333:** A first press, or a press of the confirming control, for a task identity that no task holds saves nothing, and is answered with the not-found page (fdr R-103, R-105; SDD § 4 EX-6, "it shows UX-S10 when its target is gone"; UXD UX-S10).
- **CP-334:** When the save behind the confirming control fails for a reason that is not a refusal, the saved data and the tracker's state are as before the press. The console shows a message naming the move and the error. The browser says in plain words that the move to `cancelled` did not happen and nothing was changed, at the task's row or status. No Python error text reaches the page (fdr R-107, R-108; NFDR QC-56, QC-57; SDD § 4 OB-3). The words follow CONTENT.md § Message patterns, Error, the failure that is not a refusal.

### Reuse by the deletions

- **CP-335:** The confirmation's behaviour in CP-321 to CP-326, CP-329, CP-331 and CP-333 is UXD UX-I2's, which holds for deleting a project, deleting a task and moving a task to `cancelled`. In this change only the move to `cancelled` uses it. This change adds no delete control and no confirmation for deleting a task or a project, and states no rule that pins their absence (SDD § 4 EX-12 leaves each control to its own slice). What is particular to the move is the sentence's and the confirming control's words, and what the confirming control saves. The confirmation is built so that the later deletions can use it without restating those behaviours. How it is built for that is development-design's to decide, and design review checks it.
