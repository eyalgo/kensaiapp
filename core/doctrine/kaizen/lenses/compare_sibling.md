# Compare against a ratified sibling — which mechanics only this skill has

**A different job from a lens, and not the audit's.** Lenses ask what an artifact reveals about the
instrument. You read two instruments side by side and ask which parts of this one nobody else needed.
No artifact is involved and nothing is judged through its output, so the rule opening the lens README
is not yours to fail.

**Not blind, and never handed to a round's reader.** You need two skills by definition. The
cold-read's reader is given one substance file and nothing else on purpose — hand it a sibling and
the fresh read is gone. This runs where that read is already spent.

**When: at the escape hatch** — the moment the loop reports it cannot fix a file from inside itself
(`../skills.md` § *A fix subtracts or trades*). Also once when a skill's stack is first set up, if a
ratified sibling already exists. **Not per round.** Per round it would cost the fresh read and buy
nothing: a round's findings are about this file's own text, and that is the read the loop already has.

## Your question: which mechanics does this skill carry that a ratified sibling does not — and why?

A **ratified sibling** is any skill that does the same kind of work and has already earned the owner's
"ship it". It is the only referent available that is neither this skill's own text nor this skill's
own history — which is exactly what makes it able to see what both of those are blind to.

**Beside or upstream both qualify.** A skill standing next to this one in a set of like skills is the
obvious case; the **upstream skill whose output this one consumes** is equally valid, and where a
chain exists it is usually the strongest referent available — it is closest in shape, and the chain is
hardened upstream-first (`../skills.md` § *Hardening a chain of skills*), so it is the one most likely
to be ratified already when this read is needed. What makes a referent is doing the same kind of work,
not standing in the same position.

Expect **wider legitimate divergence** from an upstream referent, because its position genuinely is
different — so the *does a real difference earn it* test below carries more of the weight there. That
makes it a better referent, not a worse one: a difference that survives the test is informative, and
one that cannot answer it was never about position in the first place.

Work **mechanic by mechanic**, not line by line. A mechanic is a thing the skill does: a gate, a
precondition, a resolution step, a computed value, a recorded artifact. For each one this skill has
and the sibling lacks:

- **What does the sibling do instead?** There is usually something, and naming it is usually the fix.
  It may make the operation not care, delegate the guarantee to a tool that already enforces it, or
  answer the hazard inside an algorithm rather than in front of it. A sibling that answers the same
  hazard in fewer moving parts is evidence, not decoration.
- **Does a real difference between the two skills earn it?** Frequently yes, and then there is no
  finding — a skill with an upstream document has inputs its sibling has none of. State the
  difference in one line. *"They are different skills"* is not that line.
- **If neither holds, the mechanic is a round's own invention that outlived the round.** Report it as
  that. The fix is to delete it and adopt the sibling's shape — not to refine it. Refining is what the
  rounds were already doing when they reached the hatch.

Then the **reverse pass**, which is cheaper and finds a different class: what does the sibling have
that this skill does not? A capability the sibling earned in its own rounds is not automatically owed
here — but an absence nobody chose is the shape `../skills.md` § *The shape that cannot see an
absence* describes, and this is the one read positioned to notice it.

## The sibling is read-only — and so is every fix that follows from this read

**Nothing arising from this read may modify the sibling.** Not the read itself, which like every file
here emits findings and edits nothing; and not the fix the `kaizen-fix-author` decides from it, which
lands on **this** skill and only this skill.

The reason is what "ratified" means. The sibling earned the owner's "ship it" against evidence, at a
version. Editing it to close a gap found while auditing a *different* skill un-ratifies it silently:
its version moves, no round audited the change, no evidence covers it, and the next skill to use it as
a referent is comparing against something nobody signed. One read would have quietly spent two
ratifications.

So a defect you genuinely find in the sibling is **surfaced, not acted on** — reported separately as an
observation for the owner, never folded into this round's fix. If it deserves work it deserves its own
round on that skill, with its own evidence and its own ratification. That call is the owner's, and
they make it knowing the reach.

## What you are not doing

- **Not auditing the sibling.** It is the reference, not the subject. You are reading it to learn what
  it does instead — not to grade it.
- **Not writing the replacement.** You report the mechanic, the sibling's answer, and whether a real
  difference earns it. The `kaizen-fix-author` decides, as with every other finding.
- **Not treating parity as the goal.** Two skills doing different work *should* differ, and "make them
  the same" is never the finding. The finding is **"these differ and nobody can say why."**
