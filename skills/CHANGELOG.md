# Changelog — `skills`

Each entry records a change to what a user of a fresh clone installs, runs, types or reads in `skills/`. It names the project the change was made under and cites the commits that made it. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Upgrading

- **tools** — Install `osv-scanner`, `semgrep` and `gitleaks` on the machine that runs `development-security`, for example with `brew install osv-scanner semgrep gitleaks`. The skill runs all three on every run, and where one is missing its report says that scanner did not run and its verdict reads `reported`. None of the three needs an account or a login. (`c457ff6ba`, `d25671bdf`)
- **dev-skills** — Type `project-finish-line` where you typed `project-dod`: the CPO skill that declares a project's finish line is renamed, and the old name is not kept. That covers its launcher call (`launcher.sh project-finish-line <project>`) and setup seeds that name it. (`950438dee`, `436ce1bf9`)
- **dev-skills** — Type `project-dod` where you typed `project-agari`: the CPO skill that declares a project's Definition of Done is renamed, and the old name is not kept. That covers its launcher call (`launcher.sh project-dod <project>`) and setup seeds that name it. (`da89cda94`)
- **tools** — Install uv for skills' commands to run. A skill command that ran `python3` starts `<CORE>/tools/locked_python.sh` in its place, which runs the command on the Python the instance pins, through uv, and stops without uv rather than falling back to `python3`. (`98a82927a`)
- **dev-skills** — Type `seed-pick` where you typed `nemawashi-pick`: the skill that picks a project's next seed is renamed, and the old name is not kept. That covers its launcher call (`launcher.sh seed-pick <project>`) and its `--skill` and `--prompt seed-pick/thin` names. Run `shukuba-refine` or `nemawashi-refine` again for a route report written before the rename: the `build-idea` queue refuses a pick row that names `nemawashi-pick`. (`128b8c3d0`)

### Added

- **product-development** — `tobiishi-seal` writes `close_verdict.md` in the sealed folder under `trail/<key>/`, in its seal commit, when the chain hands it the close's passing line. The file holds that line, `close passed — <n> scenarios passed at <short sha>`, and one newline. A seal handed no line, including one launched by hand, writes no such file and seals as before. (`3043a07b8`, `1081f986e`, `5416354f4`)
- **product-development** — `skills/qa/` holds QA's first skill, `red-behaviour`. It sorts each behaviour a change's spec states into new or changed, kept, or untouched, and describes Behave scenarios for the first two. It reads the product's way in from the `**Behave way in:**` line of `docs/nfdr.md` and picks none of its own. It describes the scenarios and runs none, writes no file and makes no commit, and the chain does not launch it yet. The `qa` agent now reads the instance's `qa` overlay. (`314296cdd`, `111f05004`)
- **product-development** — `stations-blind-review` is a PM skill that reads a seed's route as a fresh run that did not cut it. It maps every ruling the seed records to the station whose bar proves it, and writes what no bar carries, what a bar contradicts, what cannot be checked and what cannot be met in order to `docs/stations-blind-review/<seed>_review.md` in the project. It edits no journey file. `stations-from-seed` names it as the move after a re-cut, and reads that review to fix the route from while it still describes the route. (`b5de3730e`)
- **tools** — `development-implementation` asks the chain's commit-shape check about its closing marker's body before it commits the marker, and answers each task the check names. (`2d932b698`, `1d05f0ac1`)
- **tools** — `changelog-line` is a Content Editor skill that the change chain runs on a change's branch, after implementation and before code integrity. It writes the change's entry under `## [Unreleased]` in the `CHANGELOG.md` at the change's product path. It removes the `docs/what_left.md` entries whose whole want the change completes. A part-complete entry stays. Where the product path keeps no `CHANGELOG.md`, it writes nothing there and the step still finishes. (`d8755a31b`)

### Changed

- **product-development** — `session-close` still names each journey move the session owes and starts none before you say so. Once you tell it to run one, it runs the move through the agent of the seat that owns it without asking again, and then tells you which seat ran it and what the run did. A move that ends in your own answer stays yours. (`4a79a400e`)
- **product-development** — `red-behaviour` commits QA's record alone, with a `No reach:` line saying why and no red commit, when the product's recorded way in reaches none of the behaviours the change adds or changes. Its record template states the two forms a record takes, a red record and a no-reach record, and that a record holding a slot of each is refused. (`33075ba0a`, `9b2457d46`, `96065a55d`)
- **product-development** — The `red-behaviour` skill's `SKILL.md` no longer says that the closing step is not built. It says that after the security review the chain runs every scenario on the change's final code, on every change whose card says `behave`. The close stops the walk when a scenario does not pass, when Behave reports none or when a developer commit changed the scenario folder, and it never runs QA's step again or asks for its red or its record. (`5589d3133`)
- **product-development** — `development-implementation` and `development-design` each ask QA to change its scenarios when the run cannot go on without a change to one of them, or to a step definition it runs on. Each seat asks at most once, only on a change QA's step applied to, and the ask's text is its reason: the scenario or step definition, what must change in it and why. The run writes the ask, uncommitted, at the path `chain_development.py --qa-ask-place` prints, composes no path of its own and makes no commit after it. `development-implementation` states that a plan written before the ask stands and that the ask is the developer's only way back to QA's files. `red-behaviour`, run again on an accepted ask, reads the ask's reason from the change's ask record under `system/logs/` before it writes the scenarios, beside the spec and never in its place. (`47072fee4`, `5f9071861`, `11168799b`, `e91bb730b`)
- **product-development** — `red-behaviour`'s `SKILL.md` states that the chain takes one ask from the developer and one from the Architect, each with its reason, and runs QA's step again for an ask it accepts. It says neither seat's skill makes an ask yet and that `red-behaviour` does not read the reason. (`5c9c20e9b`)
- **product-development** — The comment in `development-design`'s change design template names a fourth state in which no way in is recorded: a `**Behave:**` line that reads `behave` with no `Behave way in` line. (`084366308`)
- **product-development** — `stations-from-seed` checks its route against every ruling the seed records, not only the seed's `## What it is`. Where a ruling lists the pieces the work must have, a station's line names each piece, even when that makes the line longer than a clause. (`900b55664`, `a45eef582`)
- **tools** — `development-security` runs `osv-scanner`, Semgrep CE and `gitleaks` on every run, beside the dependency audit the NFDR names and never in place of it. `osv-scanner`'s advisories are answered as the audit's are: an allowed fix, an exception, a question for the owner or a report for the PM. One advisory both report is answered once. Semgrep's and `gitleaks`' findings are judged with the code review's other candidates, and none counts only because a scanner reported it. `security-report.md` has a `## Scanners` section after `## Dependency audit`, with one bullet each for `osv-scanner`, Semgrep CE and `gitleaks` giving the version and what it found, and each `## Advisories` row names which tool reported it. A `gitleaks` finding is named by file, line and rule id, and the secret is never shown. (`c457ff6ba`, `d25671bdf`)
- **dev-skills** — The skills name the `change`, `walk`, `product-docs` and `prd-and-dod` launchers in place of `chain-development`, `chain-change`, `chain-product` and `chain-agari`. (`8ec5d752c`, `7ebc2d82c`, `36fb2dd25`)
- **product-definition** — `development-specs` runs every rule a spec calls unchanged against the change's base commit and records the result in Verified Claims. A rule that does not hold at the base is restated. (`aa4d9422c`, `2d6b88329`)
- **tools** — `nemawashi-retire` reads a folder seed's paths off the index. When its commit is refused only over files the retire itself moved, it declares them and commits once more. (`1bcdea3f6`, `f32374252`)
- **dev-skills** — `development-implementation` saves a task's failing tests under `— red`, whatever the reason for saving them. A red that an earlier run saved under another label gets a saved-red note in place of a rewrite. A pause names the last task that landed. (`6d8016036`, `f4f137a3c`, `0ee2a13bc`)
- **tools** — The skills that write a record into a change folder, and the plan's instruction template, point at the rule that a record names no machine. (`7ed8e9e0e`)
- **dev-skills** — `stations-from-seed` reads each test a station's bar requires to fail today against the product's code, and confirms that the defect can make the test fail. (`c63eb2e72`, `adfd158db`, `4b89070fd`)
- **dev-skills** — `shukuba-refine` also reads the `change` launcher's record when it checks that no walk is in flight on a change. (`333051e69`)
- **dev-skills** — The skills that write a record, and the plan's instruction template, state that a record names no repository address. That address is the `<owner>/<name>` of the repository the record is committed to. (`068b8be3c`, `b7b25d2ef`)
- **dev-skills** — `project-setup` asks how much is written down before the work starts. Software offers everything, just what it is and when it's done, or nothing; a product without code offers the last two. Under nothing, setup asks no product questions, writes no answer files and starts no walk. (`2de6fae45`, `2fcd9747f`)
- **dev-skills** — `project-stamp` stamps the setup seed the card's `Definition:` names: `full` the whole definition chain, `prd-and-dod` a seed that ends at the Agari, and `none` no seed. It refuses `--type no-code --definition full`, and a no-code product defaults to `prd-and-dod`. (`2de6fae45`, `2fcd9747f`)
- **product-development** — `stations-from-seed` reads the product's SDD when it has one. Each station takes a whole slice, and a station that takes only part of one is cut only together with an item raised on the SDD's companion asking for the slice to be split. A product with no SDD is cut as before. (`af553f48f`)
- **tools** — `dependency-repair` runs the commit builder's changelog check, `merge --check-only`, on each of its merges to `main` before any merge lands. When one check refuses, it merges nothing. Each merge carries a `CHANGELOG.md` entry that the skill writes on the branch, or a `--user-invisible` reason that the paths the branch changes decide. (`a1dc5a723`, `eca03a01a`, `8b967dad6`)
- **tools** — `changelog-line` writes a change's entry in the `CHANGELOG.md` of each product path the change's branch changes, not only in the one at the change's own product path. A change to a root file a fresh clone gets is logged in `core/tools/CHANGELOG.md`. It still removes what-left entries at the change's own product path only. (`bb01ee97a`)
- **product-development** — `test-driven-development` no longer ranks a real collaborator above a fake for a unit test, and names the testing doctrine and the product's language guide as the standard its tests meet. `development-code-integrity` checks code against the language guide, `arch_defaults.md` and `testing_doctrine.md`, and repairs code that builds its own collaborators, or a unit test that touches a real resource, instead of passing it. `development-implementation` brings a module it edits up to that standard in the same change. `development-design` and the plan's instruction template state each new test's layer and the fakes it hands in. The `test-driven-development` references hand a collaborator in instead of patching the module that holds it, and the deferred-decisions template no longer counts those two conflicts as a packet departure. (`676753b27`, `74a2ea7ff`, `6a237a23e`, `18034fd5a`, `92b140213`, `598c2a9e0`)
- **tools** — `development-security` and `dependency-repair` hand their bookkeeping to `core/tools/security_bookkeeping.py`: they read the audit's output, compute each exception's lapse date, write the exception record and its upkeep row, and check the report's verdict line through it. Audit output the tool cannot read counts as an audit that cannot run, and the closing message quotes the tool's refusal. What each skill decides is unchanged. (`499fecfaf`, `143ffc33a`)
- **product-foundation** — `product-architecture` tells the Principal Architect to make the Behave call for each product during its definition, on the `**Behave:**` line of the NFDR's § 9 *Test strategy*. A product we own, with code, that a person uses is `behave`. Any other product is `none — ` with one of four reasons: it has no code, it is kensaiapp's own machinery, it is work inside someone else's repository, or it is a trial or a benchmark. A product whose card reads `Test command: none` answers `none`. Where no reason fits, the call is raised on the NFDR's companion and the line keeps its placeholder. `product-card` copies the NFDR's answer onto the card's `**Behave:**` line word for word, and leaves the card's line as it found it while the NFDR has not made the call. (`f3e103e96`, `eca5952ca`, `59457a50e`)
- **product-development** — `product-architecture` also picks how a product's Behave scenarios reach it, where the product's Behave call is `behave`: a command, a server or a browser. It makes the pick once per product, on the `**Behave way in:**` line of the NFDR's § 9, below the `**Behave:**` line, and a later run leaves a picked way in as it stands unless freshly authorized. Where the Behave call is `none — <reason>` it writes no such line, and while the call is not made or no way in fits, the line keeps `command | server | browser`, with the pick raised on the NFDR's companion when none of the three reaches the product. `development-design`'s design for a change that alters behaviour has a section, *Testing the change from outside the code*, that says how the change is tested through the way in the NFDR records, and picks none of its own. (`f6a5c8c10`, `f8c7785ff`)
- **product-development** — `red-behaviour` now writes the change's Behave scenarios into the product's `.behave` folder and commits them as the change's red once the chain's verdict accepts them, then writes QA's record, `qa_record.md`, in the change folder and commits it. It first asks the chain whether QA's step applies, and where it does not, it writes no file and makes no commit. It takes every path it writes from `development_path.py target --kind qa`, and the chain now launches it. (`421e756fe`, `885588186`)

### Removed

- **tools** — The `readme-status` skill is removed, so `launcher.sh readme-status <project>` no longer starts a run. `shukuba-refine` no longer writes a `readme-status` row in its `## Next moves` table. (`a3fcb00e5`)

### Fixed

- **product-development** — `tobiishi-seal` now joins the change's audit branches before it delivers, so the sealed change folder under `trail/<key>/` holds the audits' `flow_findings/`. Before this, a seal could skip the join, and the audits' findings never reached `main`. After a proved delivery the seal removes each joined audit branch and its worktree, and after a failed delivery it keeps them. Both steps now run through `core/tools/seal_audits.py`, and a join that fails stops the seal before it delivers. (`edc11be08`, `3311c90b1`, `243dd20fe`)
- **tools** — `changelog-line` writes its report with no `version:` line, so the change chain's changelog step commits again. Each report had copied its template's marker, and the commit builder refuses a new file whose marker is not `1.0.0`. (`5120cb790`)
- **product-foundation** — `product-architecture`'s `SKILL.md` and `README.md` name the NFDR's verification map as § 10, where the template has it, not § 9. (`f6732fbc9`)
