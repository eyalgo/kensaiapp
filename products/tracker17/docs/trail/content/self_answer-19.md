### 3.2 — No rule says how a message shows a location whose path is not valid text

- **Bucket:** 3. Raised from downstream — an item from a seat that did not write the verbal language
- **Verdict:** answered
- **Why:** A path the tracker prints is written as the machine names it, and a byte in it that is not text is written as a backslash, an x and the byte's two hex digits, such as `\xe9`. The item has no draft, so I answered from scratch.
  1. **Whose it is.** The edit lands in `CONTENT.md` § Grammar and mechanics. The rule fixes how a value is worded, which is this seat's craft, and it changes no fact about the product. It commits no person and no outside party. I can name no ground I am missing, so it is not the owner's. The item's premise is that a Linux path may hold bytes that are not UTF-8. The two sources in the header support it. `docs/SDD.md` § 4 RT-3 says "The tracker runs on macOS and Linux", which is the platform statement behind the item's `docs/nfdr.md` § 9 citation.
  2. **It cites its occurrence, so "not until it occurs" does not apply.** The item gives a command and its output, which is the second kind of occurrence in `<CORE>/../skills/pm/.claude/skills/shukuba-refine/prompts/rich.md` § "A gap is carried only where it occurs". I did not import the product, because a run leaves the product's checkout as it found it. I ran the underlying step alone: decoding `b'/tmp/caf\xe9/data'` as the filesystem does and then encoding it to UTF-8 raised "'utf-8' codec can't encode character '\udce9' in position 8: surrogates not allowed", on Python 3.15.0. The product has three places that do this. `main.py` prints `_ready_line` and `_unreadable_line` to standard output. `UnreadableSite.__init__` in `web/routes.py` encodes the page with `self._page = pages.unreadable_data_page(location).encode("utf-8")`, which is built when the start binds. So the failure is wider than the item's heading says. It reaches the ready line, the unreadable-start line and the page, and the rule is for any path the tracker prints. That is the narrowing I name.
  3. **Check 2: one question, three possible forms.** The item says showing the path at all is a wording call. It is one question, not two, and I weighed three answers.
     a. Leave the path out. This breaks three settled statements: `docs/SRS.md` AC-7, "a start shows a plain message naming the data's location"; SRS NFR-8, "writes to the console ... the saved-data location"; and UXD UX-S9, which "names its location". The reader also loses the one fact needed to find the data.
     b. Replace each bad byte with a mark that stands for a character, such as U+FFFD. It is not plain ASCII, so a terminal that can't write it brings the same traceback back. It gives two different bad bytes the same look. It also states a character where there is none, which § Voice, "State only what the tracker established", does not allow.
     c. Write the byte as `\xe9`. It is plain ASCII, so no terminal or page that can write a path can fail to write it. It keeps different bytes apart, and a developer can read it back to the folder. I confirmed the form can be produced: decoding `b'/tmp/caf\xe9/data'` as UTF-8 with the backslash-escape handler printed `/tmp/caf\xe9/data`, and `/tmp/café/data` came through unchanged. The rule names no function. I used Python only to confirm the form exists.
  4. **Check 3, against the document and its inputs.** A backslash is in no banned-punctuation row, and the colon rule is untouched. Localization already lists file paths among what is "Never translated", so the path stays as it is and only its form is ruled. No sentence is added, so the 20-word and three-sentence limits hold, and the ready line is already at the cap. The reading bar bars "a word a first-time reader would have to look up", and a hex escape is not a word. The reader of such a path made it. My answer to item 3.1 writes its path by this rule, and the two were decided together.
  5. **Check 4, the failure paths.** Empty: a path of all valid text comes out unchanged, so a normal start prints the same string as before. Stale and concurrent: the path is fixed at start, and the other-tracker line names no path. Refused and absent: no case reaches this rule. **Not covered, and named.** A folder name that really holds a backslash, an x and two hex digits reads the same as an escaped byte. A valid character that the terminal's own encoding can't write is a different cause with the same traceback, and the rule does not reach it. Whether the tracker must start from such a location at all is not stated upstream, which says only macOS and Linux. The rule makes the start say something true if it does, and moves nothing upstream.
  6. **The other reading, and what tipped it.** I was close to leaving the item for the owner, because how a path looks is partly taste. What tipped it was that the rule commits nobody, that the ASCII reason is not a taste, and that I know of no taste reserved on it. If the owner says a start from such a location should be refused, no message shows the path and this rule has no work.
  7. **What the fold writes.** One bullet in § Grammar and mechanics for a path the tracker prints, with the byte form and the example, and a review note for it. Localization needs no change.
